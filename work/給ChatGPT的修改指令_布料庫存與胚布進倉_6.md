## 指令 1：布料庫存 vrt_fabric_stock_control_v1.html — Fabric Warehouse Reference 要匯進「收發與結餘」

**現況問題**
- 在「布料庫存」匯入倉庫群組的 `Fabric Warehouse Reference`（含 Daily Record 工作表）時，系統顯示：
  「附件標示的 72 筆範例未計入實際庫存，請至『收發與結餘』新增紀錄」。
- 這份檔案是**正式資料**，不是範例。Daily Record 的每一列就是實際的收料／發料／結餘紀錄，應該直接進「收發與結餘」。
- 輔料（Accessories）的倉庫檔也用同一個頁面、同一個流程匯入。
- `FABRIC STOCK UPDATE xx.SEP` 檔案目前可正常解析，維持原本流程不要改壞。

**請修改**
1. 匯入辨識：偵測到 Fabric Warehouse Reference（或含 `Daily Record` 工作表）時，不要判定為「範例」。
   把它當成「收發與結餘」的正式來源，逐列轉成收發紀錄（日期、布號/物料、顏色、單位、收入量、發出量、結餘、備註、來源檔名＋工作表＋列號）。
2. 移除或改寫「72 筆範例未計入」這個判斷：
   只有檔案裡明確寫 `Example`／`範例`／`Sample` 的列才略過。其他列一律視為實際紀錄。
3. 匯入前先顯示**預覽**，包含：
   - 新增幾筆、重複略過幾筆、無法辨識幾筆（列出原因）。
   - 各單位（yds / m / kg / pcs / roll）的收、發、結餘合計。
   - 使用者按「確認匯入」才寫入。
4. 去重鍵：`日期 + 物料/布號 + 顏色 + 收發類型 + 數量 + 來源列`。同一份檔重匯不可重複加總。
5. 不可覆蓋既有的庫存與收發紀錄，只做新增。已存在的紀錄內容不同時，列入預覽「差異」讓使用者選擇，預設略過。
6. 單位照原檔保留，不要自動換算。無法辨識的單位列為警告，不要默默丟掉。
7. 匯入完成後由既有的 smart sync 自動推上雲端，☁↑ 狀態列要顯示上傳筆數。
8. 只改這一頁需要的匯入邏輯，不要動其他模組與雲端 API 結構。版本號加一，並在頁面「說明」加一行更新紀錄。

**驗收**
- 匯入 Fabric Warehouse Reference 後，「收發與結餘」出現對應的收發紀錄。
- 再匯一次同一份檔：新增 0 筆、全部重複略過。
- FABRIC STOCK UPDATE 15.SEP 匯入結果與修改前相同。

## 指令 2：胚布進倉 vrt_fabric_delivery_greige_center_v1.html — 刪除的列被雲端拉回來、雲端待重試

**現況問題**
- 本機刪掉 7 筆舊的重複紀錄後，本機剩 38 筆／252,213 yds。
- 自動同步 Pull 時，又把雲端上那 7 筆拉回來，變回 45 筆／274,925 yds。
- 雲端狀態一直顯示「雲端待重試」，本機的刪除沒有傳到雲端。

**請修改**
1. **刪除要能同步**：本機刪除時記錄 tombstone（id、刪除時間、刪除者）。
   - Push 時把刪除一起送上雲端，讓雲端也移除（或標記 deleted）。
   - Pull 時遇到本機 tombstone 較新的紀錄，不可再加回來。
2. **合併規則**：用每筆紀錄的 `updatedAt`／`deletedAt` 決定新舊，較新的一方勝出，不要單純「雲端有、本機沒有就補回」。
3. **「取代（Replace）」匯入模式**：使用者選擇取代時，要以本次匯入結果取代雲端快照。舊的列要在雲端一併移除，不可只更新本機。
4. **修正「雲端待重試」**：
   - 找出 push 失敗的原因（逾時／payload 太大／驗證錯誤），在狀態列顯示實際錯誤訊息。
   - 若是資料太大，請分批上傳。
   - 失敗的變更保留在佇列，下次自動重試，並顯示待上傳筆數。
5. 刪除仍需使用者確認（保留現有 confirm），且只刪使用者選的列。
6. 不要動其他模組、不要改雲端 API 的共用結構。若 smart sync 共用檔（vrt-smart-sync-v3.js）必須修改，請先說明影響哪些頁面再改。版本號加一。

**驗收**
- 刪除 1 筆 → Push 成功 → 重新整理頁面並 Pull → 那筆不會回來，筆數和 yds 合計維持刪除後的數字。
- 另一台電腦開同一頁 Pull，也看不到被刪的列。
- 狀態列顯示「完成」，不再停在「雲端待重試」。
